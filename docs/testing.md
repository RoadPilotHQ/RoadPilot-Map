# Test and fixture policy

This document defines how RoadPilot-Map is tested and how test fixtures are created, stored, reviewed and maintained.

It describes **project policy**. It does not claim that any particular use of ATS or ETS2 game data is legally permitted. The legal questions are tracked as L1 and L2 in [Open questions](open-questions.md).

## Principles

1. **Synthetic data by default.** Fixtures are written by hand, or generated by code that is checked in. They are never copied or derived from real game files.
2. **Minimal.** A fixture contains only the data the test needs.
3. **Deterministic.** The same code and fixtures always give the same result, on every machine.
4. **Runnable anywhere.** `cargo test` passes without ATS or ETS2 installed, without network access and without any local configuration.
5. **Reviewed together.** A fixture is changed in the same commit as the tests that use it.

## Real game data restrictions

These rules apply to the repository, CI, releases and any other published artifact:

- No original ATS or ETS2 game files in Git.
- No extracted game assets or map data in Git, including partial extracts, excerpts, hex dumps and data derived from them.
- No real game archives in automated tests or CI.
- No game data in test fixtures, expected-output files or snapshots.
- No game data in releases, packages or any other public artifact.
- No game data pasted into issues, pull requests, logs or documentation.

Opt-in tests against a local installation (see below) follow these extra rules:

- They run only when a developer explicitly enables them.
- They treat the game installation as **read-only** and never modify it.
- Any output they write goes to a temporary directory outside the repository and is deleted afterwards.
- Their output is never committed, uploaded or published.

## Test categories

| Category | Purpose | Data | Runs in `cargo test` |
|---|---|---|---|
| Unit tests | Individual functions and modules | Small inline inputs | Yes |
| Integration tests | Interaction between crates and pipeline stages | Synthetic fixtures, temporary directories | Yes |
| CLI tests | Arguments, output, exit codes and error handling of the `roadpilot-map` binary | Controlled synthetic inputs | Yes |
| Local installation tests | Behavior against a real local ATS or ETS2 installation | The developer's own installation | No (explicit opt-in only) |

### Unit tests

- Live in a `#[cfg(test)] mod tests` block next to the code they test.
- Use small inline inputs, such as byte arrays, string literals or values built in code.
- Do not access the file system, the network or a game installation unless the code under test is specifically about that, and then only inside a temporary directory.
- Example today: `crates/roadpilot-map/src/lib.rs`.

### Integration tests

- Live in the crate's `tests/` folder (`crates/<crate>/tests/*.rs`).
- Test how crates and pipeline stages work together, using synthetic fixtures.
- Create any files they need in a fresh temporary directory, and remove it afterwards.
- Must be deterministic and must not require ATS or ETS2.

### CLI tests

- Live in `crates/roadpilot-map-cli/tests/`.
- Run the compiled binary through `env!("CARGO_BIN_EXE_roadpilot-map")` and check standard output, standard error and the exit code.
- Pass all inputs explicitly (arguments, paths in temporary directories). They must not depend on the user's home directory, configuration or game installation.
- Example today: `crates/roadpilot-map-cli/tests/cli.rs`.

### Local installation tests (opt-in)

Such tests exist in `crates/roadpilot-map-formats/tests/real_installation.rs` (parses every sector) and `crates/roadpilot-map/tests/real_installation.rs` (builds the road network of the whole map). Every such test must follow these rules:

- It is marked `#[ignore]` with a reason, so ordinary `cargo test` and CI never run it.
- It needs the environment variable `ROADPILOT_MAP_GAME_DIR`, pointing to the game installation folder.
- It runs only when a developer enables it explicitly, for example:

  ```powershell
  $env:ROADPILOT_MAP_GAME_DIR = "D:\Games\American Truck Simulator"
  cargo test -- --ignored
  ```

- If it is run but `ROADPILOT_MAP_GAME_DIR` is not set or not valid, it fails with a clear message instead of passing silently.
- It never modifies the game installation and never commits, uploads or publishes game data or its output.
- It asserts properties (for example "parsing succeeds" or "at least one road exists"), not exact values copied from game data.

The gate is implemented by marking the test `#[ignore]` and reading `ROADPILOT_MAP_GAME_DIR`. If the variable is missing, or the folder has no `base_map.scs`, the test panics with a clear message. To cover both games, run the test once per installation.

## Fixture layout

Fixtures are added only together with the first test that needs them. Empty directories and placeholder files are not created in advance.

```
RoadPilot-Map/
├── crates/
│   └── <crate>/
│       └── tests/
│           ├── <topic>.rs
│           └── fixtures/              Fixtures used only by this crate
│               └── <format-or-feature>/
│                   ├── README.md      What the fixtures are and how they were made
│                   └── ...
└── tests/
    └── fixtures/                      Fixtures shared by several crates
        └── <format-or-feature>/
            ├── README.md
            └── ...
```

- **Inline first.** If a test input fits comfortably in the test code, keep it there.
- **Crate-local next.** Fixtures used by one crate live in `crates/<crate>/tests/fixtures/`.
- **Shared last.** Only fixtures used by several crates live in the root `tests/fixtures/`.
- **Grouped by format or feature**, for example `archive/` or `sector/`.
- **Locating fixtures:** tests build paths from `env!("CARGO_MANIFEST_DIR")`, never from the current working directory.

## Fixture rules

- **Prefer text.** Use a small text format where it is enough.
- **Binary fixtures** (for example synthetic archives) are preferably built in test code from documented bytes or with a small builder function. A checked-in binary fixture must be small, and its README must describe its layout and how it was created.
- **Document non-obvious fixtures.** Each fixture folder has a `README.md` that states the purpose of each fixture, the expected behavior, how it was created, and which tests use it.
- **Expected output** (golden files) may be checked in next to the input, but only for synthetic input. It is updated deliberately and reviewed like code.
- **Line endings:** Git on Windows may convert line endings on checkout. When the first byte-sensitive fixture is added, a `.gitattributes` entry must mark the fixture files so Git does not convert them.
- **Malformed input** is a valid fixture. Tests for corrupt or truncated data are encouraged, because game files are treated as untrusted input.

## Determinism

Tests must not depend on anything they do not control:

- **Time:** no current date or time. Pass timestamps in explicitly.
- **Randomness:** no random values. If randomness is needed, use a fixed seed.
- **Network:** no network access.
- **Machine:** no machine-specific absolute paths, user names, locale or environment, apart from the documented opt-in variable.
- **Order:** no reliance on file system iteration order or hash map order. Sort before comparing.
- **Parallelism:** tests run in parallel, so each test uses its own temporary directory and shared state is avoided.

## Temporary output

- Temporary files are written under the system temporary directory (`std::env::temp_dir()`), in a directory unique to the test, and are removed when the test finishes.
- Tests never write into the repository, the user's home directory or a game installation.
- Tests use small hand-written helpers for temporary folders. Adding a test helper crate (for example for temporary directories) is a normal dependency decision and must pass the [dependency policy](architecture/crates.md#conventions).

## Review checklist for fixture changes

- [ ] The fixture is synthetic and contains no real game data.
- [ ] It is as small as possible.
- [ ] It is in the right place: inline, crate-local or shared.
- [ ] Non-obvious fixtures are documented in the folder's `README.md`.
- [ ] The tests that use it are in the same change.
- [ ] `cargo test --workspace` passes without ATS or ETS2 installed.
